# 34편 면접 · 포트폴리오 — 평가 시스템 설계 모의 면접 + 개선 한 바퀴 + GitHub · 이력서

실전 8 · AI 평가의 마지막 편입니다. 예상 면접 질문 "사내 문서 Q&A 에이전트의 평가 시스템을 설계해 보세요"에 23~33편에서 만든 것으로 답하는 틀을 정리하고, 우리 DART 에이전트를 실제로 한 바퀴 고쳐 본 뒤(오류 분석 → 한 곳 수정 → 영향받은 문항 + 회귀 세트만 다시 실행 → 관문), 결과를 GitHub README와 이력서 문장으로 옮깁니다.

면접 질문은 공개된 면접 준비 자료(techinterview.org · PracHub 등, `CURRICULUM.md` 3절)를 바탕으로 만든 **예상 질문**입니다. 특정 회사가 실제로 낸 질문이라는 뜻이 아닙니다.

## 실행

## 모의 면접 — 답의 틀(9단계)
| 단계 | 말할 것 | 이 섹션 |
|---|---|---|
| 1 성공 정의 | 틀리면 누가 무엇을 잃나(사내 문서: 틀린 규정 안내 · 권한 없는 문서 노출) | 23 |
| 2 평가 대상 | 답 정답성 · 근거/인용 · 검색 도구 궤적 · 거절/권한 · 비용/지연 | 23 · 32 |
| 3 데이터 · 라벨 | 질문 로그 → 시험지 · held-out, 오류 분석, 결정권자 라벨 | 25 · 26 · 30 |
| 4 채점기 · 루브릭 | 예/아니오 기준, 코드 먼저, 열린 기준만 판사 | 27 · 28 · 29 |
| 5 판사 검증 | TPR/TNR · kappa, dev/test 분리 | 30 |
| 6 통계 | 신뢰구간 · 짝 비교 · 문항 수 | 31 |
| 7 회귀 관문 | 회귀/능력 세트, 문항 단위로 막기 | 33 |
| 8 운영 모니터링 | 정답 없는 신호로 표본 → 같은 채점기 · 표류 | 33 |
| 9 반복 | 오류 분석 → 한 곳 수정 → 영향 문항 + 회귀 → 관문 | 26 → 34 |

## 실제 결과 (2026-10-19 강의 녹화 실행)
- **계획만 먼저(01)**: 6문항 모두 계획이 의도대로 바뀜 — n14 · q38 재무 → 공시 검색, q32 연도 2024·2023 → 2025·2024, q51 · q52 · q54 뉴스 검색 → 거절. 계획 담당 6번 $0.0001.
- **다시 돌리기(02)**: 41문항 · $0.0344 · 약 35분(문항당 중앙값 $0.0047 → $0.0006, 180초 → 117초 — 같은 모델 이름이어도 26편 때와 단가가 다르다).
- **전후(03, 코드 채점기 v3)**: 고치려던 계획 실패 **0/6 → 5/6**(후 95% 44~97%, 짝 차이 +83%p) — q38(배당 비교)만 이번엔 계획에서 거절해 여전히 틀림. 회귀 세트 **35/35 → 32/35**(n11 · q35 · q33, 짝 차이 −8.6%p, 95% −18.0 ~ +0.8). 다시 돌린 41문항 전체 35 → 37(+4.9%p, 95% −8.7 ~ +18.5, 0 포함).
- **관문**: `01_gate.py --runs planner_v2` → **실패**(회귀 32/35). 능력 세트 6 → 11/18, 전체 77.4 → 81.1%. 평균은 올랐지만 관문은 문항 단위라 막는다 → 병합하지 않는다.
- **떨어진 3문항은 지시문 탓인가(과제 1)**: v1 · v2로 각 2번 더 돌리니 v1에서도 n11 1/2 · q35 1/2 · q33 0/2 — 흔들림이었다. 세 문항 모두 10/18 세 번 기록이 없어 "한 번 맞힌 것"만 보고 회귀 세트에 넣은 문항이다(33편이 적어 둔 한계). 다음 바퀴는 회귀 세트를 여러 번 돌려 다시 고르고, 흔들리는 문항은 능력 세트로 보낸다.
- **다시 돌리다 생긴 일 두 가지(숨기지 않는다)**:
  1. 첫 시도는 7문항 뒤 프로그램이 멈췄다: 지시문 v2가 검색어(query) 없는 작업을 냈고 워크벤치가 `KeyError: 'query'`. v1에서는 나오지 않던 계획 모양 → `sec12/team.py` `clean_task`에 검사 한 줄, `02_rerun.py`는 문항 하나가 터져도 나머지를 계속 돌리게 고침($0.0046 버림).
  2. 둘째 시도는 녹화용 복사본에 공시 검색 자료(`data/rag`)를 빠뜨려 공시 검색이 모두 오류였다 → 관문 **16/35로 실패**, 그런데 **계획이 그대로인 문항까지** 떨어졌다(q15 · n02 · n22 · n26). 지시문 탓이면 계획이 바뀐 문항만 떨어져야 한다 → 기록을 열어 원인을 찾았다($0.0214, 기록 `data/rerun34_nodata.jsonl` · `compare34_nodata.json`). 관문은 이유를 가리지 않고 막는다. 막히면 먼저 읽는다.
- **포트폴리오(04)**: `PORTFOLIO.md` — 문제 · 평가 대상 · 데이터셋/라벨 · 채점기/루브릭 · 판사 검증(N과 구간) · 통계 · 회귀 관문 · 개선 한 바퀴 · 한계 · 다시 해 보기. 숫자는 각 편 README 실측과 `data/compare34.json`에서만.
- **공고 역량 10개 × 23~34편**(23편 jobs.json, Python 제외): 10개 모두 한 편 이상. 공고엔 드물지만 면접 자료에 자주 나오는 통계(5) · 판사 보정(2) · 공개 벤치마크(2)는 31 · 30 · 24편. 사후학습 · RL(4)은 다루지 않음.
- 이번 편 유료 호출 합계: 약 $0.13(다시 돌리기 · 과제 풀이 · 실패한 시도 포함, 상한 $0.40).

## 면접 질문
1. "사내 문서 Q&A 에이전트의 평가 시스템을 설계해 보세요" → 위 9단계 순서로. 성공 정의(누가 무엇을 잃나)부터, 판사는 검증한 뒤에, 숫자에는 N과 구간을, 마지막은 관문과 반복.
2. "평가 결과를 보고 출시 여부를 어떻게 설명하나요?" → 막는 조건 · 통과한 것 · 아직 모르는 것 세 칸으로. 이번 판정은 **보류**: 고치려던 5/6은 좋아졌지만 회귀 3문항이 떨어졌고, 원인(흔들림)을 확인한 뒤 회귀 세트를 다시 골라 재검증한다(과제 2).
3. "개선했다는 걸 어떻게 증명하나요?" → 바꾼 곳은 하나, 같은 문항 짝 비교와 구간, 영향받은 문항과 회귀 세트를 함께. 평균만 보면 +4.9%p로 좋아 보였지만 구간이 0을 포함하고 회귀 3문항이 떨어졌다.

## 과제
1. 관문이 막은 문항(n11 · q35 · q33)과 새로 거절한 q38이 지시문 탓인지 흔들림인지 v1 · v2로 다시 돌려 가려 본다.
2. "출시해도 되나요?"에 답하는 판정 메모를 이번 숫자로 쓴다(막는 조건 · 통과 · 모름).
3. 이력서 문장 검사기: 숫자 출처 · 분모 · 막연한 말을 코드로 검사해 부풀린 문장을 거른다.
