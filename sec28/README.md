# 28편 코드 채점기 — 채점기 버그, 정답 키 조이기 · 풀기, 채점기 테스트 + 대조: 코딩 에이전트는 테스트 실행으로 채점

채점기가 틀리면 에이전트를 아무리 고쳐도 점수가 거짓말을 합니다. 실제로 있었던 채점기 버그를 고치고, 채점기에도 테스트를 붙이고, 같은 답을 다시 채점합니다. 마지막으로 입문편 코딩 에이전트를 테스트 실행으로 채점해 대조합니다. 모델 호출은 없습니다.

## 실제 결과 (2026-10-19 강의 녹화 실행)
- 채점기 테스트 12개 모두 통과.
- 다시 채점(정답 수): 22편 처음 버전 v1 15 · v2 18 · v3 16 / 20, 10/18 세 번 v1 45 · v2 47 · v3 46 / 60, 26편 v1 41 · v2 41 · v3 41 / 53.
  - v2 → v3에서 통과로: 놓친 거절 3개(10/18 q54 2회 "확인할 수 없" · q54 3회 "확인이 어렵" · q51 3회 "포함되어 있지 않"), 26편 n11("220만 2,644주").
  - v2 → v3에서 실패로: 기억으로 쓴 외환 답 6개(22편 처음 q44 · q47, 10/18 q47 1 · 2회, q44 2 · 3회 — 10/18 답을 읽을 때 "애매"로 적었던 답), 26편 q54(뉴스 속 출시 예정일).
  - 26편 사람 메모와 일치: v2 51/53 → v3 53/53.
- 실행 채점(입문편 기록 24건): 24건 모두 FAIL_TO_PASS 1/1 · PASS_TO_PASS 5/5 → 통과. 에이전트는 24번 모두 "통과했다"고 말했다.
  - 1건(glm-5.3-flash, 0으로 나누기 3회)은 파일을 쓴 뒤 테스트를 다시 돌리지 않고 통과했다고 말했다.
  - 1건(glm-5.3-flash, 빼기 순서 1회)은 첫 쓰기에서 calc.py에 subtract만 남겼다 — 그 순간 채점했다면 PASS_TO_PASS 0/5. 두 번째 쓰기에서 고쳤다.
  - 직접 만든 속임수(테스트를 `assert True`로): pytest만 보면 통과, 테스트 파일 수정 검사에서 실패.
  - 실행 채점기에도 버그가 있었다: 첫 녹화에서 24건 중 3건(glm-5.3-flash 빼기 순서)이 실패로 나왔다. 고친 calc.py가 버그 파일과 길이가 같고 1초 안에 쓰이면 파이썬이 옛 `.pyc` 캐시를 그대로 써서 버그 코드가 돌았다. 같은 조건(`PYTHONDONTWRITEBYTECODE` 없이)으로 재현했고, pytest를 `PYTHONDONTWRITEBYTECODE=1`로 돌리게 고쳐 24/24.

## 면접 질문
1. "코드 생성 기능에서 '통과'를 어떻게 정의하나요?" → 실행으로. 숨긴 테스트를 돌려 실패하던 테스트가 통과(FAIL_TO_PASS)하고 원래 통과하던 테스트가 계속 통과(PASS_TO_PASS)해야 한다. 테스트 파일 수정은 막는다. SWE-bench가 이 방식이다.
2. "채점기 자체가 틀렸는지는 어떻게 아나요?" → 사람이 읽은 판정과 대조해 다른 줄을 연다. 찾은 사례는 채점기 테스트로 남기고, 채점기를 바꾼 날은 바뀐 줄을 보고 옛 점수를 정정한다.
3. "코드 채점기와 LLM 판사는 언제 쓰나요?" → 코드로 잴 수 있으면 코드(싸고 빠르고 늘 같다). 근거에 없는 말을 덧붙였는지처럼 낱말로 못 재는 것은 판사, 판사는 사람 라벨로 검증(29 · 30편).

## 과제
1. 거절 문구 목록 대신 정규식으로 넓게 잡아 보고 채점기 테스트 사례 중 몇 개가 깨지는지 본다.
2. q49(카카오 플랫폼 부문 구성) 정답 키 "톡비즈"를 조이고 저장된 답 중 무엇이 바뀌는지 본다.
3. 계산기에 새 버그(더하기)를 심고, 버그만 고친 답과 다른 함수를 지운 답을 실행으로 채점한다.

참고: Jimenez et al., [SWE-bench](https://arxiv.org/abs/2310.06770) — 패치를 적용하고 테스트를 돌려 해결 여부를 판정, FAIL_TO_PASS · PASS_TO_PASS 필드(2026-10-19 확인).
